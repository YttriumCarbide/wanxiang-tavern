# 当前发布模式

纯静态版直接在浏览器运行全部API逻辑，配置与密钥由各玩家自行提供。存储、部署与兼容方式以[静态化适配](静态化适配.md)为准。下文保留的本机HTTP路由用于开发隔离测试，不是部署依赖。

# 角色、剧本与聊天 API

## 游戏入口与接口设置

酒馆顶部“设置 → 接口设置”选择角色生成、剧本、酒馆交流或快速闲聊用途，填写Base URL、模型和API Key。命名并保存API连接预设后，四个用途都能从“选择API预设”直接应用；提示词预设在独立标签页导入选择，支持SillyTavern多层消息、开关、排序、编辑与导出。新安装没有导入预设，需先导入再从门口生成。默认最大输出 **32768 tokens**，旧默认值会迁移，自定义值保留。服务仍需支持所选输出上限。

首次召唤长景月汐后，靠近青色召唤门点击“召唤角色”打开详情页。万象召唤术从世界书官设角色中抽取未拥有的来客，无限召唤术调用角色API，混沌召唤术各以50%概率选择官设或AI。无限和混沌可填写世界观与角色愿望，AI分支将愿望作为当次brief发送；未配置时打开设置，保存后继续。每次成功召唤扣1份契约，失败或取消不扣。靠近紫色副本门点击“进入剧本”，加载时生成本章。失败或取消保留原内容，不自动重试付费请求。

保存命名的API连接预设会将URL、模型、Key和兼容参数一起保存在本机，重启后仍可选用。仅保存当前接口时，Key是否跨重启保留仍由“记住当前接口密钥”开关决定。已保存Key不回显到输入框，显示“已配置”；提示词预设、世界书和诊断导出均不携带Key。旧预设若此前已丢失Key，需要重新填入并保存一次。

## 角色协议 v3

角色API在`<wanxiang_json>...</wanxiang_json>`内一次输出一个JSON对象：`{schemaVersion:3, setting:{...}, data:{...}}`，先设定层，再数据层。旧的“纯文字＋game_data”传输协议已停用，旧世界书仍可恢复。

| 分类       | 内容                                                                                                    |
| ---------- | ------------------------------------------------------------------------------------------------------- |
| setting    | 姓名、性别、年龄、外貌、职业、性格、经历、攻击方式、两个技能动作                                        |
| 动作结构   | 普攻、技能均为 `name/description`；职业也用 `name/description`                                          |
| 文体与长度 | 设定集文笔，人物本身的稳定设定；提示词目标为纯文字1000～1500参考tokens，经历约200字；不作为代码拒收条件 |
| 世界观     | 酒馆位于多元宇宙裂隙。来客被召唤前四周变白，再睁眼站在酒馆召唤之门门口；不擅自发明公共契约或酒馆阴谋    |
| data       | 模板、生命、蓝量、普攻数值、行动次数、动画类别、技能费用与效果、被动参数                                |
| 名称来源   | 名称仅在setting生成；代码按同序槽位继承到战斗数据                                                       |

所有机械规则在输入的 `mechanics` 分区：九种Buff／Debuff、四种被动位置、效果形状、费用和动画类别完整列出。`world`只提供公共世界观，`design`只规定设定文体，`request`只放本次要求。AI先按人物定位决定动作与效果，再填合理数值。

代码校验完整JSON与游戏数值，继承设定名称后将data编译成战斗定义；setting去掉JSON外壳后组成正常的文字设定。角色条目只保留 `name/title/worldbook/formatVersion` 与编译后的 `combat`，不持久化原始设定对象或原始data。原始响应只在页面内存的最新一次生成诊断中保留，刷新即清除，不进入角色条目。后续剧本和聊天用途通过`settingOnly`读取人物ID、名称和纯文字世界书，不能携带战斗JSON。

`setting.personality`标准输出为字符串；输入兼容完整的`{name,description}`对象，将两段文字以“名称：描述”合并，保留全部内容。名称最多30字，合并后仍受2400字上限约束；缺项、非文字、空白和未知字段仍拒收。生成与本地重校验共用此处理，诊断保留原文并记录转换，游戏数值和技能规则不变。动态Schema附有明确的字符串示例，已有世界书通过`{{outputSchema}}`获得同一说明。

计数由本机锁定版js-tiktoken按o200k_base完成，只算整理后正文，不算JSON符号、字段名和数据层。第三方模型可能使用其他分词器，此参考不是服务商计费数。六名固定角色已经按同一结构补全，阅读见[角色设定集.md](角色设定集.md)，源文件为`src/content/official-characters.js`；现有战斗数值不变。

## 剧本协议 v3

标签内输出`{schemaVersion:3, story:[五段小说正文], data:{...}}`。story前四段依次在第一至第四场普通战斗前展示，第五段只在最终Boss战获胜后展示；不额外要求总开场、战前／战后、说话人、动作、对白结构。每项字符串可以用转义换行包含多个自然段。文风、视角、节奏、篇幅及描写方式由所选预设主导，项目只提醒逐渐推进故事并留下伏笔，不要求开篇宣告任务目标。

data沿用原有title/synopsis/setting/tags/npcs/nextHook字段和范围。NPC仍只含name/setting，代码分配ID；nextHook仍为setting/map/artNodes。数据层解析后保存为程序元数据，不混入正文。story只保存一份文字，不再合成第二份action/dialogue/text。

代码只检查五段文本、完整JSON、字段类型、技术容量和数据层合法值，不检查小说采用哪类描写、是否发言或是否达到某个字数。诊断仅统计实际正文字符，不在发送上下文附加固定篇幅预算。旧v1/v2响应和存档继续兼容。

v8世界书迁移替换项目自带的四个剧本规则条目，保留注入位置、角色、深度、顺序和发送对象；旧规则原文停用留存，自定义文风条目及导入预设保持。格式仍经可编辑的SYSTEM @D条目注入。

## 格式约束与服务

### 标签读取协议

角色与剧本共用唯一的最终结果标签，世界书的SYSTEM @D输出格式条目与ASSISTANT示例均已更新：

```text
<wanxiang_json>
{"schemaVersion":3,"setting":{...},"data":{...}}
</wanxiang_json>
```

示意中的省略号不能用于实际输出；剧本标签内按v3 Schema提供正文和数据层。代码先提取唯一一组标签内的内容，再执行AI返回正则、安全格式修复、JSON解析与完整业务校验。标签外的其他文本或JSON不参与解析，也不保存为角色设定或剧本。JSON字符串内的同名标签按普通字符串处理。缺标签、未闭合、空内容、嵌套或多组结果均明确报错，不从其他大括号猜测结果；被长度上限截断仍拒收。

上游无需输出思考过程；兼容预设产生的其他返回文字仅留在原始返回诊断。版本4迁移只更新已有格式条目的协议段落并包裹合法示例，保留自定义补充、注入位置、开关和发送对象，不改社区预设。迁移只执行一次。

### 原始返回与本地纠错

生成失败会自动打开“生成诊断”：左侧为模型原始返回，右侧为经过安全格式修复后的校验文本，上方列出错误字段路径、JSON语法错误的位置及修复记录。长度截断、上游返回HTML或错误正文也会保留可获得的原文。成功召唤后可通过来客窗口的“原始返回 / 诊断”复查最新结果；右上角“查看原始回复”只在正对召唤门时显示角色API的上次回复，在战斗中显示剧本API的上次回复；坐在酒馆其他位置或转身背对召唤门时隐藏。两类原文各自保留在本页内存，不互相覆盖，刷新清空。没有原文时按钮禁用。可复制、下载原文；配置密钥如被上游回显会隐藏。

提取记录会显示忽略了多少标签外字符，右侧只显示提取后的JSON。自动修复仅移除首尾空白／BOM、完整外层Markdown代码围栏，以及字符串外的末尾多余逗号。不会改字符串正文、技能名称或数值，也不会补写被截断的内容、缺失字段或设定。所有修复后仍必须通过完整Schema与游戏数据有效性检查。

失败时可修改右侧校验文本，点击“本地重新校验并接收”。`POST /api/ai/validate/character|script`复用同一套校验与编译流程，不调用上游、不自动付费重试；通过后继续原本的入队或进入副本流程，保留原文供对照。剧本须保持生成时的队伍、章节和副本。诊断不进入本地世界书存储、世界书导出或后续AI上下文。

外层标签与上游JSON-only／严格JSON Schema模式冲突，因此角色与剧本生成不发送`response_format`，已保存的兼容偏好保留但在标签模式不启用。动态JSON Schema仍通过可见世界书@D条目发送，服务端始终严格检查结构、ID与游戏数值。预览显示标签协议，统计不计入未发送的response_format开销。

使用非流式[OpenAI Chat Completions协议](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)，可设置max_tokens、max_completion_tokens或不发送长度字段。预览请求只展开消息，不调用模型。提示词修改位置见[提示词修改入口.md](提示词修改入口.md)。

密钥只交给本机代理，不回显、不进浏览器世界书或预设导出；默认只在本次服务内存中，勾选“记住密钥”才落入不可静态访问的`.runtime/ai-config.json`。每趟剧本生成一次，同一趟战斗不反复生成角色。取消可中断本机等待，已提交的请求是否计费由服务商决定。

提示词与协议验收：`node tools/test.mjs --scope quality,core,server`；涉及界面合并ui。仅涉及副本推进等规则时运行ai完整副本组。测试使用隔离配置和预设目录、模拟上游；未提供真实配置时不声称完成真实付费模型联调。

## 世界书与发送统计

设置顶部的“世界书编辑器”提供SillyTavern兼容书籍/条目编辑、自动保存、导入导出、作用范围、关键词扫描及激活报告。详细能力、源码对照和游戏中的生命周期映射见[SillyTavern世界书适配.md](SillyTavern世界书适配.md)。本地书与配置保存在`.runtime/ai-config-world-info/`，测试通过`AI_WORLDINFO_DIR`隔离。人物正文和标签可在角色池修改，刷新后仍保留，不改战斗数值。

“最终发送预览 / TK”与实际生成共用`generationRequest`。每条消息分别统计o200k_base正文token，总数另加消息封装与结构化格式开销估算；最大输出额度单列。生成诊断保留当次最终messages、统计及上游usage，失败时也保留。预览不调用模型、不推进时间或概率状态。

setting中的额外`*_note/*_comment`等明确注释字段会被剥离并记录原值，避免因无执行含义的备注整份拒收；必填字段、类型和游戏数值仍严格验证。默认提示词明确各层白名单和主动/被动形状，自定义预设预览会警告旧协议、非JSON示例及重复上下文。

## 来客档案与剧本素材

召唤结果用卡片显示姓名、性别、年龄、职业及基础属性；外貌/职业/性格/经历分段阅读。普攻、两个技能可展开，展示实际费用、目标、效果值和设定中的动作。展示层从已保存的纯文字世界书提取段落，再与combat合并，不存第二份原始setting/data，也不把combat送给剧本。旧设定无法拆分时仍可完整阅读。底部只有“加入队伍”和“原始返回”；加入后保存到酒馆角色池，不自动更换六人出战队伍。

剧本生成之前，服务端按与实际副本相同的encounterSpec确定五站敌人ID、名称、数量、位置和可能行动。新增可编辑“副本怪物图鉴”世界书，按本趟场景关键词激活相关七种怪物（六种普通怪加选定Boss）。初次升级会加入剧本作用范围，之后不覆盖用户改动；删除或停用后不擅自恢复。怪物行动仅表示能力，不表示已造成伤害或胜负。

默认剧本预设的可编辑文风层使用{{scriptStyle}}，读取prompts/script-style.md；可以直接把这一层改成自己的文风文字。规则与五站原创示例一起提供具体动作、人物口语、节奏和套话约束。说明与参考见[文风与怪物设定说明.md](文风与怪物设定说明.md)。

## 社区预设适配更新

游戏创作要求和Assistant完整示例已迁移到单一世界书条目，通用预设只提供消息框架；第三方预设保留顺序、身份、扩展及内嵌正则。注入顶栏、按条目选择API、正则阶段与具体限制见[社区预设使用.md](社区预设使用.md)。格式要求与动态JSON Schema由可见的世界书SYSTEM @D0条目注入，不再额外追加隐藏格式消息。

## 示例污染修复

版本5将内置的完整角色／剧本示例改为默认停用的编辑参考。此前格雷完整档案以ASSISTANT @D1常驻发送，容易诱导模型复写这个角色；现在默认仅发送本次任务、实际资料和可见的动态Schema。剧本中的格雷若属于真实队伍，人物设定仍正常发送。

迁移仅停用内容未被改写的内置示例，保留正文、位置、API对象、用户自定义示例与第三方预设。输出条目明确区分本次要求和格式示例。后续用户主动开启示例的选择在重启后保留。服务端若发现上游JSON与本次发送的完整ASSISTANT示例原样一致（忽略空白和对象键顺序），在诊断记入不阻断接收的`output.source`参考信息并保留原始返回，不自动付费重试；改写后的新内容仍走完整校验，不能据此判断AI创作是否足够新颖。

## 仅校验格式与游戏数据

角色设定不检查必须包含哪些词、不匹配固定召唤句式，也不按总TK数或经历150～260字拒收；history仍须是非空字符串，技术上限与其他长文本统一为2000字。剧本不按文风、剧情内容或正文总字数拒收，字数只统计供查看。创作目标留在可编辑世界书。两种API及本地重校验共用此规则，保留必填字段、数据类型、技能槽位、五场节点顺序、合法说话人ID和可执行效果／数值的检查。

## 名称只生成一次

角色仍使用schemaVersion3的setting/data结构。setting保存姓名、职业、普攻、两个技能的name及人物描写。data不再输出name、title、attackName，data.skills也不再输出name；数值、费用、目标、效果、动画模板等仍在data。两个data.skills按数组顺序对应setting.skills。代码在编译时直接继承这些名称，不依赖文本匹配。

新请求的动态Schema与可编辑世界书格式规则均使用去重结构。旧v3响应可继续带重复名称，输入校验把它们作为可选兼容字段，编译一律以setting为准；例如“桥梁匠人”与旧data.title的“驿道桥工”不同也会通过，原始返回不被改写。运行中的combat仍包含完整名称，既有存档格式不变。世界书版本6仅更新内置的重复生成说明和原版参考示例，保留条目位置、开关、自定义补充与第三方预设。

## 剧本复用已有身份与场次

剧本只用speaker引用提供的角色ID，不重复生成角色名／档案；新增NPC只在npcs中声明一次姓名与设定，代码分配npc-1等ID。scene不再要求AI复写encounter编号，五项数组按本次encounters顺序书写，代码统一赋值0～4；旧v2返回可带encounter兼容字段，实际绑定以数组顺序为准。显示用text仍由action与dialogue组合，不需要模型重复写一遍。动态Schema、世界书输出规则与停用参考示例同步更新，角色与剧本的旧存档继续读取。

新一趟剧本请求带独立visitId和最近三篇标题／概要作为避重复索引，旧剧本全文不会作为范文重发。已确认历史仍单独承接；生成结果不从旧篇缓存代替。若五段正文与已存剧本完全相同（忽略空白），诊断增加output.repetition参考提示，仍按格式规则接收，不自动重试。

## 1.2 地图路线与延伸

副本门先打开环境与地点选择，不立即调用模型。确认地点后，input.exploration携带程序生成的map/sequence/seed描述符；服务端重新计算五场encounters，怪物名单和固定环境规则与引擎一致。每次仍生成五段story，数据层和标签协议保持1.1约定。

角色池的exploration为五张地图分别保存六个可选副本地点、完成次数、近期已确认历史及后续线索。只有完整五场胜利后消费该地点并产生后继；失败、中途返回和重复回调不推进。下一次请求带选中后继的continuation，并仅带当前地图路线历史。AI的nextHook.map和artNodes属于故事元数据，不直接改变程序选定的地图、敌人或属性；古堡内部等故事地点可以复用森林主题美术。

环境加成在newEncounter应用并进入同一预演/结算状态，固定数值不随进度成长。怪物组合按节点种子与房间序号确定，确认前后保持一致，刷新存档不重新投掷已保存地点。世界书v9适配script-definition/facts/output，原文停用留存，不改社区预设或文风条目。

当前暂停游戏入口的剧本API调用，以本地五段占位正文测试战斗，配置与协议保留。可在设置 → 游戏选项中开启“副本 AI 剧本”，角色API不受影响。提示词预设一次导入共享库，各API在提示词预设页独立选择。世界书版本13删除奥义要求和人物对应段落，保留其他内容和注入设置并增加潘多拉。旧ultimate/quest字段只兼容剥离，不编译或显示。角色生成完成即保存角色池并同步世界书。

当前普通模式必须调用主角和剧本API，只有开发者模式可停用并使用青缘及占位剧本；具体见[开发规范](开发规范.md)。立绘导入保留原始文件字节，按角色ID引用本机图片，不再缩小后有损重编码。

## 1.3 交流与闲聊

- 两个吧台座位、圆桌、靠窗圆桌坐下后出现“交流”。先多选来客，再进入居中的文字聊天窗口。各位置有不同的程序动作池；一次打开固定抽取结果，发送时复用。聊天存入存档中的 tavernChat，连续发言附带上文，失败或取消保留输入。
- 酒馆交流使用独立 chat 配置，纯正文、HTML和显示正则均可生效。聊天正文的 HTML/CSS 在独立 iframe 中显示，模型正文脚本不运行。正文不解析为战斗命令、奖励、属性或道具，不能更改任何战斗数据。
- 快速闲聊使用独立 quick-chat 配置。路途手记底部有输入框、“闲聊”和“重置剧本”；上游必须返回唯一一组 wanxiang_chat 标签，前端只显示其内部正文。本趟闲聊留到离开副本时清空，不写进长期历史或存档。
- 聊天拼装：世界观、所在位置、选中及本次发言或上文提及的人物、聊天上文。酒馆额外发送上一趟内部剧本的纯正文；战斗闲聊只发送当前时点和已确认的本场经过，不发送未来章节。人物仅取 settingOnly，不含技能或 combat JSON。
- 世界书增加“交流合理性审查”，SYSTEM @D0、顺序9999；可在世界书编辑聊天发送对象。审查限制酒馆范围与日常互动，允许无战斗用途小礼物；战斗闲聊不能推动剧情或发放奖励。
- 预览与发送共用 chatRequest / finalizeRequest。最终后处理之后按 o200k_base 统计全部 messages，协议开销单列估算，服务商 usage 另列。上下文不足时按完整对话轮次减少本次发送的最旧消息，本地聊天保留；必需设定仍超限则明确报错。

重置调用剧本 API，复用本趟生成时保存的 generationInput，并附带当前已生成的剧本正文和本趟闲聊。代码 mergeFutureScript 只替换当前场次之后的正文；当前及此前章节、已展示手记、战斗状态、怪物配置、角色快照和奖励均不改变。请求过程中推进到下一场或离开副本，晚到结果作废。最终战没有后续战斗，按钮提示没有可改写内容。失败不覆盖旧剧本，不自动重试。

## 1.3 预设参数与扩展

提示词预设可编辑 temperature、top_k、top_p、presence_penalty、frequency_penalty、流式开关、上下文长度、回复上限和 reasoning_effort；兼容酒馆 openai_max_context / openai_max_tokens / stream_openai 字段。未设置的参数沿用接口或服务商。流式请求实际读取 SSE；聊天可逐步显示，收到完整且校验通过的响应才保存。角色和剧本使用流式上游时仍等待完整校验后接受。

API 连接配置只提供“严格无工具”和“合并含工具”两种提示词后处理，直接使用 [SillyTavern release 的 mergeMessages 实现](https://github.com/SillyTavern/SillyTavern/blob/release/src/prompt-converters.js)。先处理最终消息，再计 TK；不会另加工具定义或在游戏中执行工具。

预设导入同时保留并启用附带正则和酒馆助手脚本。设置中的“预设扩展窗口”提供小型空白宿主，实际界面由脚本生成；当前操作用途选用哪个预设，就运行其启用的脚本，切换时销毁旧 iframe 及其监听器、定时器和界面。脚本使用独立不透明源，通过有限桥接修改当前预设的提示词开关、采样参数与脚本变量，不能读取密钥或游戏 DOM、战斗数据。已适配 jQuery、Lodash、getPreset / setPreset / updatePresetWith、脚本按钮、变量、事件、常见提示词开关命令和提示消息。依赖父页面 DOM、其他酒馆插件、MVU、任意 Slash 指令或酒馆内部模块路径的脚本仍需单独适配；错误显示在扩展窗口，不假装成功。

连接设置不加载提示词脚本；提示词页按用途独立选择和启停脚本。模型列表使用 GET /models，手工模型 ID 始终保留。保存 API 预设时原子捕获当前表单，不通过先刷新连接再保存名称的流程。

脚本 localStorage 通过 /api/ai/helper-storage/:id 保存在 .runtime/helper-storage.json，按预设隔离，sessionStorage 仅在当前宿主存活期间有效；私有存储不写入预设 extensions。Izumi 1016 的 232 个提示词、32 条正则和约 1.25MB 助手脚本均可导入；上下文上限允许 400 万。原生酒馆内部插件依赖仍按兼容边界显示错误。

剧本输出格式要求标签内自然语言使用中文，保留 JSON 字段名、协议标签与程序枚举；五段正文篇幅目标为 2:1:1:1:2，第一和第五段各扩写一倍，中间三段保持通常篇幅。该要求属于世界书创作提示，不通过字数或语言检测拒收结构正确的响应。内容版本16仅向既有剧本输出条目补充这段要求，保留用户补充、开关和注入设置。

官设大纲保持连续参考文本，由AI根据真实战斗进度自行安排事件，在一次回复内完成本次旅程。story五项是展示容器，不按大纲段落逐场对应；首尾加长不限制其事件内容，也不得让已完成多场战斗的玩家仍停在入口重复交流。内容版本17移除原有的首尾内容分配要求，补充推进规则并合并内置教程大纲正文，保留用户编辑与注入设置。

输出边界提取会忽略显式思考／规划块（包括think、analysis、reasoning、带planning的预设标签和tucao）及行内代码中引用的协议标签，保留原始返回和提取位置；只读取剩余唯一输出边界内的JSON，仍拒收真实嵌套、重复结果、缺失结束标签，不扫描裸JSON兜底。

内容版本18单独增加“玩家主角与大纲代称”世界书条目，并提醒两种生成API避免在思考和说明中复述输出标签。剧本输入携带protagonistId，服务端按ID匹配在队设定并在characters.player单独标明玩家主角；不按阵容位置猜测，预设user宏使用该主角姓名。世界书和大纲中的<user>是复用代称，正文与元数据使用实际姓名、代词或合适称呼，不把主角另写成同行NPC；此为创作提醒，不新增正文关键词拒收。

## 手动记忆总结

接口设置增加独立的“记忆总结 API”，可复用连接预设，配置模型、输出上限与上下文长度；无需导入提示词预设。固定提示词位于`prompts/summary.system.md`，总结请求不加载世界书、额外人物设定、聊天预设、助手脚本或正则。仅发送内置提示词及逐条原文的id/kind/label/text。

设置的游戏选项、酒馆交流和途中闲聊均可打开“总结记忆”。待总结列表包含尚未有有效摘要的酒馆聊天楼层、本趟临时闲聊，以及已实际记录的副本叙事和战斗事件；未展示的剧本不参与。点击生成后先通过`POST /api/ai/summary/plan`预估TK并按连接上下文／输出预算分批，再顺序调用`POST /api/ai/generate/summary`。每批严格校验逐条ID完整性，失败不自动重试；手动重试只请求本次尚未完成的条目。

结果先留在可编辑的确认界面；点击“确认使用摘要”才把summary附加到对应原始消息或事件。确认前校验原文快照，记录改变、切换存档、条目遗漏或摘要无效时整批不写入；本地保存失败回滚摘要。摘要附带原文指纹，原文后续改变则自动恢复发送原文，等待重新总结。酒馆消息与副本摘要随存档／导出恢复；途中闲聊及其摘要仍按原规则在离开副本时清除。

原文不删除、不覆盖，聊天和旅途记录仍显示原文；生成及恢复存档不再只保留最近20篇副本原档。上下文组装时，已确认摘要替代对应楼层原文，未总结部分照常发送；副本路线历史副本也按原文匹配摘要。酒馆上次副本背景仅来自实际展示的叙事，剧本改写中已经历的正文可用摘要，未经历正文保留完整原文，战斗与已展示的剧情不会被摘要修改。摘要不会变成属性、物品、奖励或其他引擎数据。

界面显示输入估算、分批进度、接口usage与生成时原文／摘要参考TK；仅预估不调用上游。正文TK采用本地参考分词器，接口实际用量缺失时明确提示；编辑摘要后生成时的参考TK不会冒充新统计。

## 2026-10-18 教程与旅途记录扩展

剧本输出使用v4：根节点schemaVersion/story/data，data仅title/tags/npcs/items/nextHook；nextHook只保留setting。tags为关键词；NPC不能是队伍成员，appearance和history各至少25字，encounter为首次出现的0～4场索引。道具description最多20字，value为以太价值，encounter为实际收集场次。旧v1/v2/v3存档继续读取。archives.js仅归档实际展示过的里程碑，同名NPC合并来源；完整通关才将物资折算为以太，并用runId防止重复结算。重置剧本更新同一份剧本，冻结已经历正文及已归档数据。

酒馆正文统一用wanxiang_chat标签；交流指令独立置于wanxiang_actions标签中的JSON，含affection数组（id/delta，0～5）和agreeToAdventure角色ID数组。正文与指令分开校验和展示。relationships.js只允许队友每次下副本之间前三次正向好感增长，下副本重置次数；不修改战斗数据。所有酒馆地点与角色共用tavernChat，system/divider只表示场景切换，允许逐条删除。

教程通过实际预演与结算事件验证要求；通关后依次完成以太说明、召唤、圆桌完成一次交流及再次出发。每场战斗前自动打开手记（教程第一场手动教学除外），最终战获胜先展示结尾，关闭后才结算。地图按数字顺序解锁，各地保留独立的曲折路线。

2026-10-20协议补充：主角生成请求要求根节点`levelUpLines`提供五句符合其性格的升级台词，旧角色未提供时使用通用台词；两个技能槽均可为主动或被动，普通攻击独立。剧本`nextHook`新增`phase`，六阶段为起、承1、承2、转1、转2、合；下一次请求明确携带阶段和行动指导，历史旧伏笔继续读取。五段正文全部在对应战斗开始时展示，最终胜利单独提交完成与伏笔，不重复展示终章。新增写作要求属于提示词指导，不用正文关键词、字数或创作风格拒收有效JSON。

## 地图 API

地图与以太造物 API 均使用玩家选择的通用提示词预设，格式条目放在世界书内，可分别启停和编辑。导入预设默认应用到六种生成 API，总结仍使用独立提示词。设置中独立配置“地图 API”的连接。请求`generate/map`提交brief，可选existing为原世界、knownEnemies为已验证的跨世界敌人目录。返回world及输入TK/usage；不会自动重试。十三种美术风格与官方敌人、默认角色外貌都作为参考传入。新增世界至少一位全新Boss，扩充返回新增背景和新敌人，程序合并旧资料。

地图的id与美术map不同；新世界地图页面只显示当前前进节点。动态剧本data.encounters是五项{enemyIds:[]}; 每项1～3个不同的当前世界敌人ID，末场至少一个Boss。未登记的敌人、未知外貌/效果/位置和越界数值会拒收，原世界不覆盖。新世界使用自己的归档关键词与物品库，保存、总结与个人API资料继续只留在玩家设备。

敌人效果的target相对敌人阵营：opponents指玩家前场；self指自身；allAllies指存活敌人全体；lowestAlly指生命比例最低的存活敌人。治疗、法力、护盾及正面状态只指向敌人阵营，禁止给玩家角色施加slow。旧世界加载时移除无效slow，保留其余世界资料。Boss可使用全部已登记外貌，不限定首领皮套。地图与造物校验失败提供本次原始回复查看，不保存到长期记录，不自动重试。
