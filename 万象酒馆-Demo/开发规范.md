# 开发规范

## 开发环境

Web项目使用原生ES模块、Three.js和Node静态服务，Node版本要求22.13以上，建议使用`.nvmrc`对应的22系列。运行游戏仍可直接双击上级`一键启动.cmd`，不需要构建或安装前端运行依赖。

开发时在本目录执行 `npm ci`，恢复已提交的精确依赖锁。`npm run lint`检查JavaScript，`npm run format`统一排版，`npm run check`集中检查质量与核心规则。编辑器设置在上级`.vscode/`，支持保存格式化、ESLint诊断和Edge断点调试。

Python建模工具使用上级`建模工具/.venv`，依赖锁在`requirements-dev.txt`。新机器在该目录执行 `python -m venv .venv` 和 `.venv\Scripts\python -m pip install -r requirements-dev.txt`。日常玩法和UI开发不重新生成模型。

## 结构与边界

模块职责以`架构.md`为准。应用状态只有`app/session.js`一个所有者；控制器在`app/application.js`组装，不新增顶层可变变量或循环导入。新面板、输入方式和规则分别落入对应模块，避免重新建立巨型应用文件。

- 引擎不依赖DOM、Three.js和动画时间；规则预演与实际播放共用同一份事件。
- 行动类型为`skill/swap/reposition/item`，结算事件为`hero/enemy/swap/item`等，不能混用。回合归属统一通过`turn-flow.js`。
- 配置在启动前集中校验；行动的ID、类型、技能、AP、时间格和目标方向在进入模拟前校验，非法内容返回`invalid`。蓝量、濒死、时点阵型等动态条件在实际模拟位置检查。
- 新增数据必须有稳定ID，不用中文显示文案作为逻辑分支。用户确认的玩法规则仍以设计对照和交互文档为准。
- 全局监听器用`createEventScope`注册并销毁；Three.js资源用`createResourceScope`管理，包括替换的材质和异步晚到的资源。卸载后的异步任务不得继续渲染。
- 页面执行代码放在模块中，样式放在组件文件中。只修改对应组件的样式，响应式规则也归该组件，不建立新一轮覆盖补丁文件。
- 模板可用`html`标记方便格式化；该标记不自动进行安全转义，用户文本进入HTML前必须调用`escapeText`。
- **官设副本已废弃**：现有官设副本内容后续将逐步迁移，不要再往官设副本中塞入任何新关卡、新大纲、新事件、新怪物编排或附属功能；仅在用户明确要求时做迁移或既有兼容修复。

## 格式与依赖

JavaScript用UTF-8、LF、两空格，保留分号，由Prettier统一排版；不手写压缩代码。ESLint检查无用变量、未定义名称和领域层依赖边界。质量组还检查循环导入、CSS语法／属性／重复声明、HTML外部引用和依赖锁。

Python使用Black、四空格、100列约定，依赖独立虚拟环境。CMD内容只用ASCII命令和CRLF，中文文件名可保留；PowerShell用UTF-8 BOM，启动实现只有`launch.ps1`一份。后台进程隐藏启动，关闭前核验服务身份。

新增npm包必须精确锁定直接依赖并更新`package-lock.json`；浏览器测试从项目依赖加载Playwright，不依赖开发者私有路径。第三方Three.js保留在`vendor/`及其许可证中，不纳入自有代码格式化。

## 集中测试，改哪里测哪里

所有测试从`node tools/test.mjs`进入，一次提交本轮需要的组，收集完所有失败再修。产物统一写入`.runtime/tests/`，禁止重新建立临时QA脚本。

日常先把本次要测的范围集中写进`tools/testing/checklist.json`，再运行一次`node tools/test.mjs`。清单中的`scopes`选择检查组；`coreFiles`可限定本轮相关的核心测试文件，留空才运行全部核心用例；`browserConcurrency`最多为2。独立检查批量并行，浏览器共享一个进程，每组使用独立的服务、配置和截图目录；有依赖的检查等待前项完成，重复检查复用结果。静态构建和完整副本保留必要的顺序，不能与写同一资源的检查并行。

`node tools/test.mjs --list`只显示清单，不启动任何测试，也不覆盖上次报告。失败后统一修完，再用`node tools/test.mjs --failed`批量复查失败组；新增受影响范围可追加`--scope`。不要为了单个断言逐项启动工具，也不要反复运行已经通过且未受改动影响的范围。显式`--scope`／`--changed`仍兼容；其他清单可通过`--plan 文件路径`选择。

| 改动                         | 一次性命令                                                    |
| ---------------------------- | ------------------------------------------------------------- |
| 文档、格式、引用             | `npm test -- --scope quality`                                 |
| 数据、规则、配置契约         | `npm test -- --scope quality,core`                            |
| 界面、输入、动画、样式       | `npm test -- --scope quality,ui`                              |
| 服务                         | `npm test -- --scope quality,server`                          |
| 启动和关闭                   | `npm test -- --scope quality,launcher`                        |
| 建模脚本格式与语法           | `npm test -- --scope models`                                  |
| 按文件合并范围               | `npm test -- --changed src/app/selection.js,styles/cards.css` |
| 只重跑失败组                 | `npm test -- --failed`                                        |
| 只复核样式布局               | `npm test -- --scope layout`                                  |
| 涉及副本推进／继承的完整验收 | `npm test -- --scope core,expedition`                         |

`npm test`默认执行清单中的相关检查。UI和布局共用一个浏览器进程；布局基准覆盖普通桌面、大屏、平板、手机横屏四类实际断点。`--scope all`是重大重构或明确完整验收使用，不能用于每次小修改。普通文案和边距修改不跑五场副本。

布局基准由`npm run test:baseline`显式更新，失败时不能自动重录来掩盖问题。基准按平台保存，其他平台仍运行交互用例。浏览器默认用本机Edge，可用`TEST_BROWSER`指定通道；新机器需要提供对应浏览器。

失败后只修复并重跑失败或受新修复影响的组，可以用 `--failed --scope quality` 合并额外影响范围，报告保留其他通过结果；已通过且未再改动的组不反复运行。新用例必须验证行为，不复制实现，不为可逆的小改动扩展成大规模回归。

验收轮次默认执行硬上限（无需用户每轮重复指定；仅当用户明确要求加测或放宽时例外）：超过五条的需求按职责拆成每批三到五条；批内先一口气把改动写完，不穿插浏览器测试或全量回归；每批集中初验一次，收集全部失败后一次性修复，只复测失败及受修复影响范围一次。严禁第 3 轮验收循环；到上限仍失败、偶发抖动或卡顿即停，交接失败范围、关键日志和当前补丁，既不重复验收，也不放宽断言换绿灯。

## 开发用 AI 调用工具

`tools/ai-worker.mjs` 提供向已配置 Chat Completions 接口发起请求的标准输入调用方式。将以下配置保存在仓库根目录的 `.env.ai-worker`，该文件已由 Git 忽略。Base URL 填服务商提供的 API 前缀，脚本会补上 `/chat/completions`。仅在接口需要鉴权时填写密钥。

```dotenv
AI_WORKER_BASE_URL=https://your-provider.example/v1
AI_WORKER_MODEL=your-model-id
AI_WORKER_API_KEY=your-api-key
```

在仓库根目录运行。短问题直接输出到终端。

```bash
printf '%s\n' '{"prompt":"只回复 OK"}' |
  node --env-file=.env.ai-worker 万象酒馆-Demo/tools/ai-worker.mjs --cli ai_ask --stdin
```

文件任务读取明确列出的 UTF-8 文件，将文件内容随指令发送到接口。输入和输出路径相对于当前目录。输出目录须已存在，成功时替换指定文件，并在终端返回输出路径。启用 `json_mode` 后会校验回复是 JSON 对象，通过后才写入文件。

```powershell
@{
  instruction = "从输入日志提取错误摘要和涉及行号，以 JSON 对象返回"
  input_files = @("万象酒馆-Demo/.runtime/tests/report.json")
  output_file = "万象酒馆-Demo/.runtime/tests/summary.json"
  json_mode = $true
} | ConvertTo-Json -Compress |
  node --env-file=.env.ai-worker 万象酒馆-Demo/tools/ai-worker.mjs --cli ai_file_worker --stdin
```

文件示例使用 PowerShell 7。同样可在 Bash 中用 `printf` 传入对应的 JSON。模型对项目数据的转换结果仍按项目规则验收。

## AI 工程工作流与提示词维护规范

所有开发请求先按以下顺序形成可复核的交付记录；记录保持要点式精简，禁止膨胀为冗长审计论文，并受仓库根目录 `AGENTS.md` 中“反‘加戏’与硬性执行纪律”约束。上下文自包含只需让后续模型基于记录与当前仓库状态接手本轮，不把整段私人对话、密钥、个人存档或无关资料写入仓库。

1. **先勘察（Grounding）**：只读取或搜索与本轮需求直接相关的文件及调用路径，确认当前实现与用户手动改动；严禁全仓漫游摸底、反复重读未修改文件或因过度审计拖延落码。不能凭旧聊天记忆覆盖当前文件。
2. **规格化（`<task_spec>`）**：动手前用简短要点单说明真实文件路径、要达成的结果（What）、边界条件和对应范围内的可执行验收标准；禁止预写实现细节，严禁加入清单外任务或自创验收门槛（如未要求的逐像素视觉比对、真实上游全量采样、APK 实机复核等）。仅影响数据结构或不可逆架构的重大歧义才停下询问；非核心细节按仓库现有最简惯例落地，并在交付时附 1 句说明即可。
3. **决策摘要与补丁（`<reasoning>`、`<code_patch>`）**：`<reasoning>`仅记录基于源码证据的简要公开决策摘要、取舍、边界和影响，不输出私有思维链或逐 token 的内部推理。修改按本轮清单在工作区完整落盘；严禁顺手重构清单外文件或新增未请求的测试脚手架／工具脚本；不使用“其余代码略”等占位符。
4. **闭环核验（`<verification>`）**：严格遵守上文“集中测试，改哪里测哪里”的默认硬上限（每批先写完代码，再统一初验 1 次；如有失败，先写简短 `<error_reflection>` 定位原因后一次性集中修复，只重跑失败及受修复影响范围 1 次）。严禁“直到全部绿灯为止”的无限循环、严禁第 3 轮验收，也严禁为了“再确认一下”重跑已通过且未再改动的检查。

### 聊天与剧本提示词

修改聊天／剧本 API 或新增提示词前，先读取对应请求组装、当前提示词层级、世界书条目及输出协议。把用户给出的创作要求尽量原样作为提示词指导，按游戏当前标签、字段、ID 和上下文顺序做必要适配，放到实际负责的请求／世界书层，并核对相邻知识的引用关系；不得为了省事另造一套协议或重复一份相互冲突的预览提示词。

文风、情绪、角色焦点、对白往返与“建议／不得”类叙事要求属于模型提示词指导，不得改成依关键词、字数、发言人数或固定措辞拒绝内容的代码硬门槛。代码只校验确定性的格式、schema、游戏必须的稳定 ID、引用关系和数值安全边界。

多人剧本中，每个 `story[i]` 场景优先聚焦最相关的 2–3 名同伴或本地 NPC；同屏也尽量控制在 2–3 人。非焦点队友不参与本幕对白，只以一句旁白交代外围分工；非焦点角色不要在开场新增登场，已在场时用退场标签切出。突发事件中禁止三名以上角色逐句接龙式惊叹，群体动作合并成一条旁白。双人交涉、争论或试探应围绕同一议题展开约 3–5 个来回；单人发言含多层情绪时可由同一角色连续表达 2–3 条，避免全员平均分配台词。

## AI生成改动

AI 测试一律复用已有官设角色及其正式资料，可为校验用例改变协议结构或数值，不新增虚构角色或复制个人生成角色作为 fixture。个人生成角色、立绘、导出和存档仅保存在本机 `存档/` 或 `个人角色/` 等已忽略目录，禁止提交、上传或纳入公开构建。历史已跟踪的个人角色文件随下次同步删除；质量检查拒绝个人资料目录和独立的 `tests/fixtures/*-character.json`。

接口与正文／数据附录契约遵守[API接入.md](API接入.md)。发布版本只使用浏览器直连。密钥默认记在本机浏览器数据库，可取消“在此设备记住密钥”改为仅本页内存；默认备份与发布包始终剥离密钥。开发服务仅供隔离测试使用。模型输出必须走白名单校验，模型输出禁止eval、动态脚本、任意资源URL和修改全局官方角色。内置提示词只使用声明式数据和游戏原生设置。每趟副本固定角色身份和技能结构，升级仅在下一战边界应用代码生成的数值成长，剧情只记录实际播放过的历史。

角色生成、剧本演出或AI兼容协议改动，按实际受影响范围合并验证。纯提示词条目拆分、迁移和注入排序运行`npm test -- --scope quality,core,server`，涉及界面则合并ui；核心用例应覆盖两种API的真实请求拼装和返回校验。`ai`组使用本地模拟上游并重放五场真实浏览器战斗，仅在副本推进、资源继承、Boss规则变化或用户明确要求时运行；普通UI和提示词整理不跑该长组，不读取真实用户的接口密钥。

角色API使用schemaVersion3双层JSON，设定集1000～1500tokens、经历150～260字及召唤过程是提示词的创作目标，不能用正文关键词、固定措辞、文风或总字数拒收格式正确的角色。只校验JSON/标签、字段结构、类型、技术容量和游戏所需的ID、关联与数值范围。不可拿整个响应usage或JSON长度代替正文统计。数据校验编译后不持久化原始响应，设定去掉JSON外壳只保存文字；姓名、职业、普攻、两个技能名称仅在setting生成一次；data不重复填写，编译时按同序技能槽位继承。旧v3响应中的重复名称兼容读取，以setting为准，不进行跨层同名拒收。剧本v3分为story五段自由小说正文与data元数据。前四段对应四场普通战斗，第五段在Boss战斗开始时展示；不强制拆说话人、动作、对白，文风、剧情推进比例与建议篇幅由世界书指导，不用正文关键词或字数拒收格式正确的输出。当前v4数据层使用title/tags/npcs/items/nextHook，nextHook包含phase与setting；旧版本仍兼容。只校验格式、技术容量和数据层合法性；v1/v2仍兼容，历史只记录实际展示的正文与代码确认的战斗事实。

分层提示词采用`prompts/prompt_order`协议，输出格式通过世界书的SYSTEM @D0条目发送，默认顺序9999。完整Assistant示例保留为可校验的编辑参考，默认停用，不把某个官方角色或固定故事常驻发送成已完成回答；用户主动启用的示例可发送，上游原样回传示例可记为output.source参考信息，不能当成格式错误拒收，不自动重试；预览不能触发上游模型请求。API连接预设与提示词预设分开持久化，严禁把密钥带入提示词导出。测试通过`AI_PROMPTS_DIR`使用独立预设目录，不能改实际用户的预设文件。

生成诊断分别在session.ai.diagnostics.character和script保留各自最新原文、校验文本、错误路径和修复记录，刷新即清除，不进入世界书／AI上下文。上游最终JSON必须在唯一一组wanxiang_output标签中；先提取标签，再运行格式校验，禁止扫描标签外JSON作为回退。标签生成不发送冲突的response_format，本地始终严格校验；手动本地重校验接收右侧提取出的JSON。格式修复必须在字符串外处理，禁止猜缺失内容、改数值或跳过完整校验。本地重校验不得调用上游；失败结果不能进入角色池或副本。

世界书导入须保留未知extensions并校验已知字段，不执行脚本。预览与实际发送必须走同一generationRequest，禁止另拼一份预览；TK必须统计最终全部messages并标明参考分词器和估算开销，不能冒充服务商usage。世界书计时状态只在成功接受生成后提交，预览与失败不推进。表单自动保存归控制器生命周期管理；AI_WORLDINFO_DIR必须与测试配置一起隔离。

内置预设以[社区预设使用.md](社区预设使用.md)为准。世界书在扫描前按 API 用途过滤，输出格式条目使用 SYSTEM 深度注入，解析器保留结构校验。玩家的文风与篇幅偏好只作用于叙事正文，预览和实际请求共用组装入口。

角色、地图与以太造物共用的战斗基础玩法、状态释义及敌我目标边界，统一维护在内置世界书的 `EX：战斗基础玩法与状态百科`（`generationRule: "combat-encyclopedia"`）。更新各入口均可用的通用状态时原地修改这条百科。单个入口开放的状态写入该入口的请求参考及规则。角色或纹章专属状态（如 `meteor`、`balance`、`sacrifice`、`melody`）留在其指定玩法中。

### 新 Buff 与新地图的接入流程

#### 先确认生成范围

收到新增 Buff／Debuff 或地图需求，开发 AI 要主动询问生成范围。先按需求整理相关选项，一次问清，允许多选。用户已经明确的选项直接执行，待答期间可继续独立的玩法、测试或资源准备。任何会通过共享目录自动改变生成范围的登记，先隔离该入口或等用户确认。用户明确选择“只加到游戏”，就只接入指定的固定玩法。

- **新 Buff**。问「这个状态只给你指定的技能或关卡用，还是也允许角色生成、地图 API 生成的敌人技能、以太造物生成使用？可以分别选。」
- **新地图**。先确认需求涉及战斗背景、固定关卡还是生成世界。问「这张地图要加入地图 API 的可选战斗背景吗？是否也允许大地图发现／继续探索选用，或放进剧本的地点参考？可以分别选。」
- 如果还要让剧本、聊天或其他入口引用新内容，再确认是作为设定参考，还是允许进入结构化输出。对话能提到一个状态或地点，属于设定参考的开放范围。

#### 游戏内登记

- **Buff／Debuff**。在 `src/data.js` 的 `BUFFS` 登记稳定 ID。到 `src/status-rules.js`、`src/triggers.js` 及对应引擎模块明确目标、正负分类、叠层、衰减、净化及免疫边界。图标用 `src/buff-art.js`，说明用 `src/skill-text.js`。按本轮实际机制测试预演和结算，以及受影响的敌我目标和旧档。
- **地图**。战斗背景在 `src/content/biomes.js` 登记，地区和固定关卡用 `src/content/regions.js` 及对应的路线和遭遇配置。分别核对关卡 ID、世界 ID 和战斗背景 ID，复用既有背景时只新增需要的固定内容。新增模型或预览时核对六个卡牌锚点、场景加载和手机取景，更新 `assets/asset-catalog.json`。

#### 按确认结果接入生成

| 入口                       | 改动时核对                                                                                                                                                                                           |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 角色生成                   | `character-schema.js`、`character-generation.js` 和 `ai/pipeline/game-reference.js` 中的主动、入场和被动效果、触发条件、净化及目标边界。                                                             |
| 地图 API                   | `worlds.js` 的 `worldReference()`、新世界及敌人校验，`ai/pipeline/map-request.js` 的请求与响应，以及 `prompts/map.system.md`。分别处理战斗背景候选与敌人技能状态。地图环境规则走固定关卡和引擎配置。 |
| 以太造物                   | `equipment-generation.js`、`equipment-materialize.js`、`ai/pipeline/runtime.js` 和 `prompts/creation.system.md` 的状态、触发条件、档位及目标。                                                       |
| 大地图发现、继续探索与剧本 | 发现和继续探索会调用地图 API。只开放其中一处时，按请求模式限定候选与返回值。剧本单独核对地点参考和历史 `nextHook.map` 的兼容入口。                                                                   |

目前地图 API 的背景参考来自 `MAP_IDS`，它随游戏地图目录扩展。部分 Buff 白名单由引擎分类派生，部分历史协议直接读取登记表。新增固定内容前检查这些联动，必要时为受影响的生成入口明确列出已获准的 ID。旧存档仍按游戏完整目录及既有迁移规则读取。

每个获准入口同步核对请求参考、提示词和响应校验。测试通过现有请求预览或模拟上游验证获准 ID 可选、未获准 ID 无法被新生成结果引用，并复查旧档兼容。交付时列出实际开放的入口和测试结果。

1.2探索路线以exploration.js与content/regions.js为准，每个地点仍是一整趟五场副本。节点种子同时决定发送给AI和真正战斗的名单；环境规则在newEncounter写入纯状态，禁止界面自行计算。只有第五场胜利才能推进该地图、提交伏笔和产生后继；中途退出、失败、预览与重复回调都不得推进。地图路线历史独立保存，不随总探索次数提高怪物基础属性。改动推进时通过统一expedition组验证完整五场及接续；其余已通过范围不重复跑。

主角开局与教程涉及队伍人数和副本推进，统一合并core、ui、onboarding与expedition范围；onboarding使用隔离上游完成真实五场教学流程。旧六人存档界面测试通过legacySession显式装载兼容存档，不绕过生产开局检查。

当前版本移除奥义和觉醒任务。协议只生成普攻与两个技能，旧存档及旧返回的退役字段只兼容剥离，不进入战斗定义。立绘按角色池唯一ID保存，禁止按模板或站位写入；按原比例顶部对齐，留白补纹饰。逐字计时器归dialogue控制器，关闭及销毁时清理。

敌人意图展示的定向验证使用 `node tools/test.mjs --scope quality,intents`，覆盖三敌人同时预演、事件伤害、状态图标、单体／取消、横屏及DOM复用；ui组包含同一检查，同时选择两个范围时复用结果。

聊天与脚本宿主的定向浏览器检查使用 `node tools/test.mjs --scope quality,core,chat`。ui组包含同一检查；剧本改写只替换未经历正文，禁止更改引擎状态、已显示历史或当场章节。

主题战场、天气、走廊与房间交流的定向检查使用 `node tools/test.mjs --scope quality,core,models,environment`。environment共用一个浏览器，检查八张主题资产、各类天气与场地接触、三门入口视角、两间客房和主卧的移动及共享聊天。与ui同时选择时复用已完成的环境检查，不重复加载图册和房间。不涉及副本推进，无需运行完整五战。

仅修改房间进出位置、门口交互或交流按钮布局时使用 `node tools/test.mjs --scope quality,rooms`，只检查房间导航和共享交流，不加载地图图册。environment包含同一检查，同时选用时复用结果。

仅修改战场模型／外围环境时使用 `node tools/test.mjs --scope quality,core,models,artbook`。artbook核对新旧地图卡牌屏幕位置和大小，等待入场动画结束后截图；core比对原始地面缓冲区并验证新增装饰未侵入中央战斗区，不重复运行房间导航。

接口设置和内置预设的相关验收复用统一测试入口，检查向导跳过导入、设置保存、消息预览与正文标签。测试使用隔离配置和模拟上游。

## 2026-10-18 教程与旅途记录扩展

剧本输出使用v4：根节点schemaVersion/story/data，data仅title/tags/npcs/items/nextHook；nextHook只保留setting。tags为关键词；NPC不能是队伍成员，appearance和history各至少25字，encounter为首次出现的0～4场索引。道具description最多20字，value为以太价值，encounter为实际收集场次。旧v1/v2/v3存档继续读取。archives.js仅归档实际展示过的里程碑，同名NPC合并来源；完整通关才将物资折算为以太，并用runId防止重复结算。重置剧本更新同一份剧本，冻结已经历正文及已归档数据。

酒馆正文统一用wanxiang_output标签；交流指令独立置于wanxiang_actions标签中的JSON，含affection数组（id/delta，0～5）和agreeToAdventure角色ID数组。正文与指令分开校验和展示。relationships.js只允许队友每次下副本之间前三次正向好感增长，下副本重置次数；不修改战斗数据。所有酒馆地点与角色共用tavernChat，system/divider只表示场景切换，允许逐条删除。

教程通过实际预演与结算事件验证要求；通关后依次完成以太说明、召唤、圆桌完成一次交流及再次出发。每场战斗前自动打开手记（教程第一场手动教学除外），最终战获胜先展示结尾，关闭后才结算。地图按数字顺序解锁，各地保留独立的曲折路线。

## 装备与造物规则

装备和被动统一使用triggers.js的规则白名单，经engine.js唯一模拟结算。条件、目标、次数和基础加成不得在界面重新计算；每趟触发次数跨战斗继承。触发产生的效果禁止递归触发，击杀必须由原始伤害确认，不能把触发追加伤害造成的死亡记成原攻击击杀。造物API使用独立连接与内置提示词，源物品售价和预算由代码绑定，批量成功后才接收；已知NPC成功细化并保存才移出归档。召唤初见对话仅临时展示。

整备生成期间冻结成员身份，可调整站位与装备；副本中不得更换装备。开发者的中途返回和归档编辑同时要求总开关及分项开关，隐藏按钮不能替代控制器检查。新增定向浏览器检查合并到settings范围，包含凝聚、构造、装备、NPC、生成中整备、潘多拉事件与真实交换。

## 纯静态版本

发布入口为bootstrap.js，平台存储与请求由组装入口注入；大型资料使用IndexedDB，不将聊天正文或图片字节写入localStorage。API规则、预设处理和解析统一维护src/ai/pipeline，server中只保留Node测试适配器，不另写第二份规则。公开发布目录由tools/build-static.mjs白名单生成，任何个人资料不得作为构建输入。内置世界书只从项目协议和已批准四位角色正文构造。定向验证增加static范围，必须使用无API服务的文件站点并覆盖仓库子目录；具体见静态化适配.md。

## 整备与对话记忆专项

整备、角色编辑、触摸拖拽及记录归档使用 `preparation` 范围，复用 `tools/test.mjs` 的清单入口。只覆盖桌面和当前手机横／竖屏需求，不重复跑副本通关。截图等待面板入场动画完成，不截取透明过渡帧。

总结以完整问答为最小聊天单元，一条玩家发言和紧接的AI回应合并提交；未回应发言不单独总结。确认后派生摘要绑定双方原文校验，原记录保留，编辑任意一侧使摘要失效。副本经历仍按已展示条目总结。

## 2026-10-30 原图资源与场景加载

角色采用卡面一张、透明正面全身一张；Gal用同一全身文件裁半身，世界贴片按脚底锚点落地并带接触阴影。提示词及原始文件哈希记录在assets/character-art.json，原图不得另行压缩。资源变更后执行build-asset-catalog生成尺寸和版本目录，静态构建自动更新。场景统一使用scene-loading与asset-store，等待图像解码、模型解析和首帧就绪；Cache API不可用时正常退回网络。酒馆后台仅串行预取原始字节，不提前解码全角色或上传GPU。刷新点由content/tavern-visitors.js管理，新增位置须避开家具并校验脚底地面。
