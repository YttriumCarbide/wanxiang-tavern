【副本剧本 · 创作目标】
让故事随旅程逐渐推进，并留下伏笔。
文风、视角、节奏、篇幅和描写方式由当前预设主导，五段正文像小说一样自然书写。
【副本剧本 · 游戏对接】
本趟战斗路线与敌人名单由encounters提供，战斗结果由游戏结算。前四段在对应普通战斗开始前展示；第五段在Boss战获胜后展示。
历史只记录实际展示过的正文，nextHook保留为未发生的后续。数据层不改变本趟的地图、敌人或战斗数值。
【副本剧本输出格式 / SCRIPT v4】
最终结果放在唯一一组 <wanxiang_json> 与 </wanxiang_json> 内，标签单独成行。代码只读取标签内的JSON；标签外内容不属于正文或数据。
标签内为一个完整JSON对象，根节点只含schemaVersion/story/data；schemaVersion为数字4。
story是恰好五个字符串：前四项依次是第一至第四场普通战斗对应的小说正文；最后一项是最终Boss战获胜后的收尾。每项可包含多个自然段，用JSON转义换行。正文自由写作，无须拆解为说话人、动作、对白或开场等字段。
data只含title/tags/npcs/items/nextHook。tags是关键词，供副本记录像世界书一样触发；不再生成概要、环境背景、后续场景类型或美术地点描述。nextHook只保留setting后续线索。npcs最多12名，绝不能是队伍成员；每项包含name/appearance/history/encounter，外貌与简略经历分别至少25字，合计至少50字，encounter是初次出现的战斗索引0～4。items只记录玩家在正文中实际收集的道具，最多24项，每项包含name/description/value/encounter，description为20字以内的中文描述，value是非负整数以太价值，encounter是收集发生的战斗索引0～4。不提前归档尚未遇到的人或尚未收集的物品。副本所有收获在完整通关后折算成相同价值的以太，可在酒馆兑换；不直接修改装备、技能或战斗属性。
正文仅生成一次，不在数据层重复。字段类型与数据层范围见Schema。

【中文输出与首尾篇幅】
标签内所有面向读者的自然语言内容必须使用中文，包括story五段正文及data中的标题、关键词、NPC外貌与经历、道具描述和后续伏笔。不得输出整段英文或其他外语正文。JSON字段名、标签名、程序规定的ID与map等枚举值保持原样，不翻译、不改写。大纲中的<user>是设定代称，生成正文时按玩家主角实际姓名与设定自然称呼。
第一场对应的story[0]与最终场对应的story[4]分别扩写到通常单段文本量的两倍。五段正文的目标篇幅比例为2:1:1:1:2；第二至第四段维持通常篇幅，不得通过缩短中间三段凑出比例。具体基准篇幅沿用当前预设与本次创作要求。
首尾加长只影响文本量，不限定各段必须描写哪些大纲事件；扩写增加有效内容，不重复凑字数，不改变五场战斗和正文展示时点。

【大纲推进与场次安排】
官设副本大纲是完整、连续的事件参考，不是按战斗分好的章节。由AI结合本次真实战斗名单、顺序与正文展示时点，自行判断大纲中的事件适合在哪场战斗前后展开；一次回复内完成整份大纲所述的本次旅程，不把大纲留待下一次API回复续写。story的五项只是展示容器，不与大纲的自然段、句子或事件一一对应，一项可以推进多个事件，一个事件也可按需要自然衔接。叙事位置与已完成战斗同步推进，不得让玩家已经打过几场后仍滞留在入口重复与NPC聊天。首尾文本加长时同样推进剧情，不强制开头只写入场交流、结尾只写固定收尾内容；第五项仍遵守Boss获胜后的已知事实，未发生的战斗不得提前写成已经胜利。
